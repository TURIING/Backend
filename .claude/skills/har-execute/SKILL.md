进入执行模式。像探索一样思考，但**跨到做**。

**核心：确认后立即执行。** 先澄清需求、提出具体动作，用户确认后再动手。产出落在代码里，不落在系统里。

**这是一个临时车道，不是正式流程。** 从用户调用 `/har:execute` 那一刻起，这个任务就是临时的：不建 `changes/`、不写任何制品、不归档、不沉淀。**永不转 `/har:plan`**。

---

## 执行流程

### 1. 自动发现并匹配已有 Spec

当用户提出需求时，先了解项目中已有的 spec：

列出所有已有 spec 能力域：
```
ls .claude/har/specs/
```

分析用户需求与各 spec 目录名称的相关性。如果发现某个 spec 与用户需求高度匹配，**必须读取该 spec 的完整内容**，然后告知用户匹配情况。

如果没有任何已有 spec 匹配，跳过此步，无需特别说明。

### 2. 检查活跃变更冲突

检查是否有活跃变更可能与当前任务冲突：
```
ls .claude/har/changes/
```

注意排除 `archive/` 目录。如果存在可能冲突的变更，提醒用户先处理。

### 3. 澄清需求

如果需求模糊，像探索一样追问、画图、对比选项，直到理解清楚。不要假装理解。

### 4. 提出具体动作并等待确认

动手前，明确告诉用户：
- **要做什么** — 具体动作
- **影响范围** — 改哪些文件、跨不跨模块

**必须等用户确认后才能执行。**

### 5. 执行

用户确认后，立即执行。执行时遵循项目代码规范（命名、注释、风格）。

### 6. 结束

- 做完就完。**不提交代码**，是否提交由用户自己开口。
- 不做任何记录、不留任何痕迹。代码改动本身就是唯一痕迹（git）。

## 澄清姿态

澄清阶段（步骤 3）沿用探索的思考方式：

- **好奇，而非命令式** — 问自然浮现的问题，不要照本宣科
- **开放线索，而非审问** — 同时抛出多个有趣方向，让用户追随感兴趣的。不要用单一问题路径引导
- **可视化** — 多画 ASCII 图来澄清思路
- **灵活** — 追随有趣的线索，有新信息时转向
- **耐心** — 不急于得出结论，让需求的形态自然浮现
- **扎根代码** — 讨论要基于实际代码库，不要凭空谈论

## 护栏

- **绝不创建变更** — 不建 `changes/`、不写 proposal/specs/design/tasks
- **绝不归档** — 不同步 specs、不提取知识
- **绝不转正** — 不提醒"可以走 plan"，不设置大小边界。用户调用 execute 就是选了临时车道
- **不要假装理解** — 不清楚就深挖，确认后再动手
- **不自动提交** — 提交需用户明确提出
- **要多画图** — 澄清时多用 ASCII 图
- **要扎根代码** — 讨论要基于实际代码库，不要凭空谈论
